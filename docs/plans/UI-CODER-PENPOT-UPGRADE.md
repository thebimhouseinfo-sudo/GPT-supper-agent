# UI Coder Penpot Upgrade Plan

## UNDER REVIEW — Direct Penpot + target-repo design/artifact ownership

**Status: UNDER REVIEW / CR REQUIRED**

This section records the current architecture direction agreed with Human. It is intentionally not canonical yet. Only a **Human-invoked CR** may clear this mark after independently reviewing the exact plan revision. Normal Reviewer PASS does not clear it.

### A. Penpot belongs to GSA/UI Coder, not to a separate lifecycle

Penpot is an operational capability used by UI Coder inside the existing UI Design workflow. It does not own a separate lifecycle, approval state, evidence family, or source of truth.

GSA Online should integrate Penpot directly as a GSA capability rather than model Penpot as a top-level Agent. The implementation may expose bounded operations such as inspect/edit/readback/export, while UI Design lifecycle/approval remains owned by the surrounding GSA workflow.

If GSA Local later implements the same Penpot behavior, Online and Local should share behavioral semantics/contracts where useful but may use different implementation languages/runtimes. This Online plan does not mutate the GSA Local repository.

### B. Design-owned workspace in the target repository

The target repository should own durable design artifacts under a dedicated `design/` area. `design/` belongs to the design workflow as a whole, not only to UI Coder.

Suggested default shape:

~~~text
design/
  designer/
    design-contract.md
    design-coverage.md
    responsive-intent.md
    asset-requirements.*
    prompts/
    references/

  ui/
    penpot/
      refs/
      draft-code/
      screenshots/
      implementation-notes.*
~~~

Repository-specific conventions may refine names, but the authority split remains:

- `design/designer/` stores Designer-owned design intent, coverage, responsive intent, visual asset requirements/prompts/references, and other reviewed design-package material;
- `design/ui/penpot/` stores UI Coder/Penpot realization artifacts that are still design-phase material;
- production source remains in the repository's normal source tree;
- production assets remain in the repository's normal asset tree;
- Tester evidence remains in the repository's test/evidence area, not in `design/`.

### C. Penpot draft code is reference material until UI Coder reviews it

Code or code-like output exported/generated by Penpot is **not production source by default**.

Target flow:

~~~text
approved/reviewed design inputs
→ UI Coder + Penpot
→ design/ui/penpot/draft-code/
→ UI Coder implementation review
→ reuse / adapt / rewrite
→ production source
~~~

UI Coder may improve framework structure, components, CSS architecture, accessibility, reuse, and maintainability, but implementation changes must not materially damage or silently change the approved UI.

The authority split is:

~~~text
approved UI design = visual/layout/responsive authority
production source = implementation authority
~~~

If implementation constraints require a material visual/interaction change, route back through the design/Human boundary rather than silently changing the approved UI.

### D. Production assets go directly to the target repository asset folder

Penpot-created/exported assets selected for actual product use should be written directly to the target repository's real production asset location according to repository convention, for example `src/assets/` or `public/assets/`.

Do not create a separate Penpot asset lifecycle or long-lived GSA asset store.

Designer-provided stable asset contracts remain authoritative where present, including identity, filename, prompt/source, intended usage, dimensions/ratio and path/slot. UI Coder should preserve these contracts.

Human may later regenerate/replace a production visual asset at the same agreed filename/path without requiring UI code changes when the contract is otherwise unchanged.

### E. Design screenshots remain design-owned artifacts

Screenshots used to review the Penpot/design result may live under:

~~~text
design/ui/penpot/screenshots/
~~~

These are design references for Human/UI Coder and are distinct from Tester runtime verification screenshots.

### F. Human connection boundary

When direct Penpot MCP use requires the browser design surface to be open/connected, GSA should ask Human only for the unavoidable connection action, such as opening the Penpot file and connecting MCP. After connection, GSA/UI Coder resumes against the same target and must not create a replacement design merely because the connection was temporarily lost.


### G. Early stand-alone Direct Penpot MCP bootstrap and Test Lab gate

Do **not** wait until the full UI Design workflow is implemented before proving the Penpot transport/output surface.

Before production UI Design integration, create one bounded **lab-only Direct Penpot MCP bootstrap** for GSA Online and run a stand-alone empirical capability experiment in Test Lab.


Tester access boundary for this bootstrap:

- UI Coder may receive only the bounded mutation operations needed by the frozen experiment;
- Tester must receive bounded **read-only** reopen/inspect/read-back operations sufficient to verify the frozen Penpot target independently;
- if independent Tester read-back cannot be provided, classify the bootstrap as `INTEGRATION_NOT_READY`/BLOCKED rather than accepting UI Coder self-report.

A transport/integration blocker is useful evidence but is **not** a successful bootstrap. PASS completion requires a functional direct lab path plus the completed stand-alone experiment and Test Lab result. A blocker must stop the chain and remain BLOCKED/INTEGRATION_NOT_READY until remediated or explicitly replanned.

The early sequence is:

~~~text
build minimal direct Penpot MCP integration
→ Human performs only unavoidable Penpot open/connect action
→ Tester authors/freezes a stand-alone Capability Test Plan
→ UI Coder executes the frozen plan against a disposable/synthetic Penpot target
→ Tester independently read-backs/verifies the result
→ record a small result manifest under test-lab/results/
→ use observed evidence to refine the later production integration plan
~~~

This bootstrap is intentionally earlier than the full P2 UI workflow. It exists to settle transport/export unknowns before the larger workflow depends on them.

Minimum empirical questions include:

- can GSA Online reach and invoke the direct Penpot MCP path reliably after the Human connection boundary;
- can UI Coder bind to the intended file/page and later read back enough structure to prove edits landed;
- can UI Coder create/edit representative screen/component content through Penpot;
- can Penpot create a representative shell-level asset and can GSA retrieve/export a usable asset file or stable asset reference;
- what exact binary/export semantics are available for handing an asset to a target repository;
- can Penpot return useful code/design-to-code reference material (for example structure, styles/tokens or generated code) that UI Coder can later review, reuse or adapt;
- what stable file/page/object references survive the operation and are sufficient for independent Tester re-open/read-back;
- what happens on temporary disconnect/reconnect, and whether the same target can be safely rebound rather than recreated.

Penpot-generated code/reference material in this experiment is **draft evidence only**. It must not be copied into production source as canonical code.

The experiment may use disposable/scratch outputs. Its durable result belongs in Test Lab as a small manifest, for example:

~~~text
test-lab/results/penpot-direct-bootstrap-<date-or-run>.json
~~~

The result manifest records the frozen test plan reference, observed capability level, asset-export/code-reference observations, stable target references, limitations and direct review links/paths where available. Large binaries, secrets and temporary design exports need not be committed to Test Lab.

A failed/partial bootstrap is useful evidence. UNKNOWN/PARTIAL/INTEGRATION_NOT_READY must remain explicit and must refine the later architecture rather than being promoted to PASS.

## 1. Objective

Upgrade the existing UI Coder specialization with a real UI design phase powered by Penpot before source implementation.

This plan is intentionally narrow.

It does **not** redesign the existing Designer role, Reviewer role, Tester role, Coder family, Job lifecycle, or planning architecture.

The purpose is to add the missing practical design-authoring capability to UI Coder while preserving existing reviewed design inputs and downstream implementation workflow.

---

## 2. Core Change

Current conceptual flow:

```text
Designer package
→ Reviewer PASS
→ UI Coder implementation
```

Upgraded flow:

```text
Designer package
→ Reviewer PASS
→ UI DESIGN PHASE
→ UI Coder + Penpot
→ Tester
→ Human
↕
UI Coder ↔ Tester
→ UI DESIGN APPROVED
→ continue implementation
```

Penpot is added as an operational capability of UI Coder.

UI Coder is not split into a new top-level Agent in this plan.

---

## 3. UI Design Phase

A new UI Design Phase is inserted after the existing Designer package has passed its required review and before UI Coder proceeds with normal source implementation.

During this phase UI Coder may use Penpot to:

- build the application shell;
- create all distinct required screen types;
- create reusable visual components;
- create or apply design tokens;
- define visual state variants;
- realize responsive compositions;
- place representative sample content;
- create/export UI assets;
- integrate generated assets required by the reviewed Designer package;
- prepare the visual shell for Tester/Human review;
- use Penpot design-to-code capabilities where useful for later implementation.

The addition of Penpot expands UI Coder capability. It must not be interpreted as narrowing UI Coder's existing responsibilities.

---

## 4. Screen Coverage Rule

The UI Design Phase follows:

```text
FULL SCREEN COVERAGE
+
REPRESENTATIVE CONTENT COVERAGE
```

Every distinct product screen required by the approved design/spec must be represented in the shell.

Repeated/generated content inside a screen does not need exhaustive design instances.

Instead, UI Coder should use representative samples sufficient to demonstrate the relevant:

- layout;
- hierarchy;
- content density;
- visual states;
- responsive behavior;
- asset placement;
- interaction affordances.

Example:

If an educational application contains Topic, Lesson List, Theory, Practice, Result, and Print screens, all six screen types must be designed.

It is not necessary to reproduce every lesson or every practice item inside Penpot.

---

## 5. UI Asset Handling

### 5.1 Penpot-native UI assets

Assets belonging to the application shell or general UI visual language may be created in Penpot and exported as real production assets when appropriate.

Examples may include:

- icons;
- simple vectors;
- badges;
- decorative UI elements;
- card decorations;
- progress visuals;
- shared UI artwork;
- other shell-level visual assets.

These exported assets may be used directly by the source implementation.

### 5.2 Reviewed generated-asset contracts

When the reviewed Designer package already defines a specific generated visual with a stable contract such as:

- asset ID;
- filename;
- prompt;
- intended usage;
- path or slot;
- ratio/dimension requirements;

UI Coder should preserve that contract.

For example, when Designer has specified a page background, card background, hero artwork, or other explicit generated image, UI Coder should:

```text
use the reviewed prompt
→ generate the intended asset
→ preserve the approved filename/ID
→ place the real asset in the UI
```

UI Coder should not casually replace such a defined visual with an unrelated icon/vector merely because Penpot can create one.

### 5.3 Generic UI primitives

Where no specific generated visual is required and a simple icon/vector/component adequately satisfies the approved UI intent, UI Coder may use an appropriate Penpot/UI primitive instead of unnecessarily invoking an image-generation workflow.

### 5.4 Content-deep assets

Assets that belong to deep/generated content rather than the shell may continue to use the existing external asset-generation pipeline.

This plan does not redefine that pipeline.

---

## 6. Tester Checkpoint During UI Design

After the shell reaches a testable state, Tester is invoked as a UI-design checkpoint.

Tester should focus on observable shell behavior and evidence such as:

- screen availability;
- prototype/navigation flow;
- visual state availability;
- responsive behavior;
- viewport overflow/clipping;
- obvious layout breakage;
- representative flow completion where the prototype supports it;
- screenshots across relevant viewports;
- concise objective observations.

Tester evidence is then presented to Human review.

Tester is not the visual decision-maker and does not replace Human subjective acceptance.

---

## 7. Human Design Loop

Human review is required because visual/UI acceptance contains subjective product decisions.

The normal loop is:

```text
UI Coder
→ Penpot shell
→ Tester
→ screenshots + observed evidence
→ Human
→ feedback
→ UI Coder revises Penpot
→ Tester retests
→ Human
→ ...
```

This loop may continue while the UI is being refined.

Routine visual refinements should not require Reviewer to re-enter every iteration.

Examples:

- spacing;
- sizing;
- visual density;
- color treatment;
- icon sizing;
- composition;
- artwork placement;
- other non-material refinements inside the approved design contract.

If Human feedback materially changes an upstream contract, the existing planning/review workflow should be used as applicable.

Examples include material changes to:

- required screen set;
- navigation topology;
- product flow;
- state semantics;
- major responsive behavior;
- reviewed asset contract.

---

## 8. UI Design Approval

When the shell has completed the Tester/Human design loop, it reaches:

```text
UI DESIGN APPROVED
```

This means the Penpot design is accepted as the visual implementation reference for subsequent source work.

UI Coder may then continue implementation using:

- the approved Penpot artifact;
- exported UI assets;
- reviewed generated assets;
- Penpot design-to-code output where useful;
- the existing Designer package and implementation constraints.

The UI should no longer need to be invented from scratch inside source code.

---

## 9. Capability / Readiness Requirement

Penpot availability must be treated as an operational capability rather than assumed from tool presence alone.

Before the workflow depends on it, the integration should be proven against the real target environment.

At minimum the system should distinguish:

```text
DISCOVERED
→ REACHABLE
→ INVOCABLE
→ FUNCTIONAL
→ GOAL_MET
```

A listed Penpot/MCP capability is not by itself proof that UI Coder can successfully author, read back, export, and continue a real design workflow.

Tester may be used to probe/verify this capability before it becomes a required dependency of the UI Design Phase.

---

## 10. Initial Implementation Scope

The first implementation should stay simple:

1. Add Penpot capability to UI Coder.
2. Add the UI Design Phase before normal UI implementation.
3. Allow UI Coder to create/edit the shell in Penpot.
4. Support full screen coverage with representative content.
5. Support creation/export of UI assets from Penpot.
6. Preserve reviewed generated-asset contracts where Designer has already supplied ID/filename/prompt/usage.
7. Add a Tester checkpoint for shell flow/responsive/screenshots.
8. Add the Human design-review loop.
9. After Human acceptance, allow UI Coder to continue implementation using the approved Penpot design and design-to-code output where useful.

Do not expand this first implementation into a redesign of Designer or the rest of the GSA architecture.

---

## 11. Follow-up Before Detailed Execution Planning

Before converting this upgrade into a detailed execution plan, perform a focused architecture review of the existing Designer system and its interfaces with:

- Planner;
- Reviewer;
- UI Coder;
- UX Coder;
- asset requirements;
- Design Coverage;
- DESIGN_READY semantics;
- Tester;
- current UI/UX Coder harness behavior.

The purpose of that review is to integrate the new UI Design Phase without deleting, duplicating, narrowing, or accidentally overriding proven existing behavior.

---

## 12. Core Principle

> Penpot adds a real UI-design workspace to UI Coder. The upgrade inserts a reviewable, testable, Human-approved UI Design Phase before source implementation without prematurely redesigning the existing Designer architecture.
