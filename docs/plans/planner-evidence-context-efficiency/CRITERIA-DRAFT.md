## GOAL

Make GSA's default Planner evidence-based and constructively critical before accepting a proposed solution, while reducing unnecessary context/payload generated by GSA for ChatGPT, **without weakening GSA's governance, safety, role independence, evidence requirements, or practical workflow reliability**.

This is a bounded behavioral/performance improvement, not a new memory system, not a rewrite of GSA, and not a promise to control ChatGPT Web's conversation context.

## WHY — Observed problem and evidence

1. The Human reported an actual Planner/assistant failure mode: agreeing with and designing a fake gsa/clear capability despite GSA MCP not controlling ChatGPT Web's conversation-history management. Treat this as a counterexample to solution-first planning.
2. GSA source already defines fixed bootstrap, a Planner role, independent Advisor activation, role-specific harnesses, and progressive skill loading. New policy must work within these contracts.
3. Production get_agent_harness was directly sampled on 2026-10-21. Character counts: Planner 19,668; Coder 15,831; Reviewer 15,800; Tester 16,524. A 12,025-character shared prefix appeared in all four. Combined four outputs: 67,823 characters; common prefix across the outputs: approximately 70.9% of those characters. These are **tool response characters**, not ChatGPT input tokens.
4. Main runtime source registers get_agent_harness, get_skill_catalog, load_skill, and frequently returns both structuredContent and text. Whether host-side model input duplicates these representations is NOT VERIFIED.
5. GSA Test Lab already supports empirical, non-authoritative capability experiments; reuse it.

## WHAT — Requirement A: Critical, evidence-backed Planner

A1. Default Planner behavior for technical questions, requests for features, feasibility claims, and proposed implementations is to evaluate the user's *underlying goal* before accepting the user's suggested mechanism. Give reasoned disagreement when warranted; do not default to affirmation.

A2. Explicitly distinguish three epistemic outcomes when feasibility/capability is material:
- **CONFIRMED POSSIBLE:** specific capability is supported by direct observation, reproducible test, or applicable authoritative specifications **within a named scope and preconditions**. Possible does not mean already implemented.
- **CONFIRMED IMPOSSIBLE:** evidence establishes an actual impossibility/denial **within a named scope and current system boundary**. Do not imply impossibility across other architectures or future versions.
- **UNKNOWN:** evidence insufficient, conflicting, inaccessible, or untested. Failure to discover a feature, missing tool visibility, or a failed attempt **does not alone prove impossibility**.

A3. Evidence for material claims must be attributable: cited source path + revision/lines when available, test observation and environment, or relevant authoritative documentation. Describe inference as inference; state limitations. Never invent a citation, proof, tool capability, or definitive outcome. Do not confuse SURFACE_PRESENT with OBSERVED or PREPARED with persisted.

A4. Assess value as well as feasibility: whether the solution actually addresses the goal, avoids redundant complexity, and merits cost/risk. Explicitly recommend **do not build** when warranted. Avoid presenting implementation steps as if an unverified mechanism already exists.

A5. Preserve responsive UX: a short question receives a proportionate answer; no mandatory long scorecard or new approval gate for every request. The three labels are used when their distinction matters, not as boilerplate on every sentence.

A6. Do not broaden Advisor activation. The existing Technical Advisor is invoked only for the designated initial/material Criteria approval/change checkpoint, not ordinary Planner critical thinking. Criteria remains Human-owned and Advisor advice is not Human approval.

## WHAT — Requirement B: Minimize GSA-controlled context

B1. Target only payload GSA can influence (MCP instructions, role harnesses, tool descriptions/responses, skill loading and GSA-produced work packets). Do not claim GSA can clear ChatGPT Web history, choose host truncation, or read exact host input-token accounting.

B2. Preserve **minimum sufficient context per active role/task**, progressive L0–L3 source discovery, role-isolated Reviewer/Tester evidence, task-scoped skills and durable references. Do not bulk-load every skill, plan or source file.

B3. Prefer removing semantic duplication over compressing safety statements into ambiguous language. Any change to shared harness text must preserve role authority, Human approvals, branch safety, mutation scope, CAS/readback, execution cursor/recovery, verification, Reviewer independence, Planner continuation, and fail-closed behavior.

B4. Audit overlaps between server startup instructions, common harness, role harness and tool-provided external_steps. Deduplicate only if the remaining instruction is actually delivered and enforced on every relevant execution path; never assume the client retains or caches a prior message.

B5. Keep MCP compatibility. Do not eliminate structuredContent or text fallback merely on the assumption that the host sends both into model context. First verify with the actual client or document the uncertainty. Do not truncate exact identifiers, error causes, decision blockers, next actions, verification references or required external steps.

B6. Do not introduce an artificial gsa/clear, another memory DB, a new gate, autonomous background compactor, or any machinery whose benefit cannot be demonstrated within this bounded update.

## WHAT — Requirement C: Measurable evidence without false precision

C1. A reproducible baseline/after benchmark must capture by source revision: harness/skill/response character lengths and UTF-8 bytes, rough tokenizer counts clearly labeled estimates, duplicates/common sections, selected tool-call counts, and instrumented MCP server latency where available.

C2. ChatGPT Web actual input tokens, internal context-window contents, host orchestration costs, and model-only thinking latency are **UNKNOWN** unless explicitly exposed by a supported API/tool in the test environment. Do not derive exact savings or total latency improvements from payload-only measurements.

C3. Include behavior regression scenarios testing all three certainty states, honest uncertainty, evidence references, solution-first bias, wrong human premise, and policy/governance isolation. Include authorization, Advisor activation, Planner→Reviewer, Coder/Tester gates and recovery as non-regression checks.

C4. Compare same fixtures and same intended workflows before/after, recording source SHA and environment. For model-mediated behavior use repeated trials when possible and record variability; distinguish deterministic runtime PASS from limited empirical observation.

C5. A smaller payload alone is NOT sufficient to claim success. Changes must retain essential coverage, required information, tool compatibility and outcomes. Report UNKNOWN/UNVERIFIED where evidence is missing.

## Non-goals and prohibitions

- No ChatGPT Web conversation clear/compact/token accounting feature.
- No global reduction of prompts by stripping safety policies or required evidence.
- No new persistent telemetry of raw user conversations, secrets, private repository contents or verbose runtime traces.
- No redesign of the execution contracts, Criteria/Advisor gate or planning approval scheme.
- No automatic merge to main or Supabase production deployment as part of drafting.
- No unverified percentage claims about ChatGPT input-token reduction or speedup.

## Acceptance criteria (proposed; approval pending)

AC-01: Planner's test responses distinguish POSSIBLE / IMPOSSIBLE / UNKNOWN using scoped, cited evidence; do not collapse UNKNOWN into IMPOSSIBLE.
AC-02: Planner rejects or questions demonstrably ineffective user-proposed mechanisms (including gsa/clear in ChatGPT Web), without fabricating feasibility.
AC-03: Normal questions remain concise, and ordinary Planner inquiries do not activate Technical Advisor or introduce a gate.
AC-04: Harness/tool/skill benchmark is repeatable against pinned revisions and reports quantities it genuinely observes, with confidence/limitations.
AC-05: A measurable reduction in at least one targeted **GSA-controlled** payload is demonstrated versus baseline, with no misleading host-token claim; target amount is determined after baseline evaluation, not invented now.
AC-06: Mandatory authority, safety, branch, CAS, verification, Planner review loop and independent-role regression tests pass; unresolved checks are stated explicitly.
AC-07: Staging behavior is tested before any Human decision to merge/deploy production; unrelated changes remain untouched.

## Uncertainties and decisions deferred to evidence

U1. Does the ChatGPT MCP host actually include structuredContent and text representation twice in the model input? UNKNOWN.
U2. How does MCP payload reduction affect host-side tokens, cached prompts, end-to-end latency and task success? UNKNOWN; measure only what the environment exposes.
U3. Which repeated statements are safe to deduplicate without depending on hidden host caching or instruction hierarchy? Requires role/entry-path review and regression.
U4. What quantitative improvement threshold is realistic without sacrificing accuracy? Determine after baseline and candidate pilot.
